# 写作与事实核对规范

这份规范管三样东西：网站文案、文档、每日邮件。目标只有一个：让读的人相信我们写下的每一句话。

## 读者

- 网站和邮件面向“想用 CongoRAG 的人”，不是面向维护者。
- 文档面向“已经决定要跑起来的人”，可以假设他懂命令行、Docker 和 PostgreSQL，但不假设他读过源码。
- 不要向读者解释我们内部怎么分工、怎么评审、用了什么提示词。读者只关心：这东西做什么、需要什么、怎么开始、哪里会坏。

## 三条底线

1. **只写已经做到的事。** 代码里没有的功能，不写；Release 里没有的产物，不说“可下载”；没有测过的数字，不写。
2. **不把仓库作者的自述当成事实。** README 里的“最快”“最强”“生产级”是作者的话，转述时要写“项目自述”，或者干脆不写。
3. **不替读者做决定。** 写清楚限制和代价，让读者自己判断。不要用“轻松”“只需一步”“开箱即用”抹掉前置条件。

## 语气

- 像给同事写说明：直接、具体、有前因后果。不端着，也不卖萌。
- 句子长短交替。该短就短。一段只说一件事。
- 多用名词和动词，少用形容词。写“默认监听 127.0.0.1”，不写“极致安全”。
- 允许写“不支持”“还没做”“会失败”“需要自己准备”。这些不是缺点，是信息。
- 第一人称只在确实代表项目时用“我们”；大多数时候用“CongoRAG”做主语，或者直接写操作。

## 不要出现的词和句式

下面这些词，出现一次就要停下来问：这句话删掉形容词之后，还剩什么信息？

- 营销词：赋能、助力、打造、一站式、全方位、无缝、极致、强大、智能、颠覆、重塑、革命性、业界领先、生产级、企业级、开箱即用、轻松上手、深受信赖。
- 空话开头：在当今数字化时代、随着 AI 的快速发展、众所周知、不难发现、值得注意的是、值得一提的是、总而言之、综上所述。
- 机械结构：首先/其次/最后、一方面/另一方面、不仅……而且……、从……到……、不是……而是……（除非真的在纠正一个误解）。
- 设问开头：想知道……吗？你有没有想过……？
- 结尾升华：让我们一起……、未来可期、开启新篇章、迈入新时代。
- 过度连接：这意味着、换句话说、简单来说、本质上、核心在于、旨在、致力于。
- 滥用破折号、排比句、三连词、每段一样长。
- 把“支持”当万能动词。写清楚支持什么、到什么程度、有什么前提。

## 结构

### 网站落地页

1. 一句话说清它是什么，给谁用。
2. 一张真实截图，配一句说明这张图里发生了什么。
3. 四到六个能力，每个能力写“具体行为 + 结果”，不写“强大”。
4. 三步开始，给出真实命令和前置条件。
5. 明确“它不做什么”。
6. 文档、GitHub、Issues 的入口。
7. 页脚：许可证、备案号、项目状态。

不要放：用户数、星数、性能倍数、客户 logo、没有的下载按钮、“即将推出”的功能墙。

### 文档

1. 这篇文档解决什么问题。
2. 需要什么（版本、依赖、权限）。
3. 步骤，带命令和预期结果。
4. 怎么确认成功。
5. 常见失败和排查。
6. 相关限制或下一步。

命令要能复制执行。路径、端口、版本号要写具体。不要在文档里写“请根据实际情况调整”来掩盖没测过的步骤。

### 每日邮件

- 事实区：仓库名、语言、今日新增星数、总星数、链接。这些来自 GitHub 页面，逐条核对。
- 摘要区：只写 README 里能支撑的内容。README 没写的，不补。
- 分析区：标题写“编辑观察”，内容是判断，不是统计。判断要给出依据，比如“今天上榜的 15 个仓库里有 6 个是 Agent 工具”。
- 不写“因为……所以上榜”。GitHub 不公布上榜原因，我们不知道。
- 不写假引言、假专家、假用户故事。
- 页脚写清楚：事实来源、生成方式、摘要可能有误、以仓库为准。

## 事实核对流程

每写一段，做四件事：

1. **找来源。** 这句话来自 README、代码、OpenAPI、ADR，还是 Release 页面？找不到来源就删。
2. **查版本。** 这条命令/默认值/端点，在当前 v5.0.2 的代码里还成立吗？
3. **查边界。** 有没有前置条件、平台差异、失败情况没写？
4. **读一遍。** 删掉形容词和连接词，看还剩什么。如果只剩正确的废话，重写。

## 已知需要修正的地方

- 根 README 说“Release 里附带启动包”，但 v5.0.2 的 Release 目前没有附件。要么补发布产物，要么改这句话。
- deployments/startup/README.md 和 docs/upgrading.md 里的版本示例还停在 3.x，和当前 5.0.2 不一致。对外发布前逐条核对。
- 文档里的“生产级”“最快”等作者自述，不进入网站文案。

## 自检清单

- [ ] 每个功能都能在代码或文档里找到对应实现。
- [ ] 每个数字都有来源和日期。
- [ ] 每条命令都在当前版本上跑过，或明确标注“未在本机验证”。
- [ ] 没有承诺未来的功能。
- [ ] 没有把 README 的营销话术当成产品事实。
- [ ] 没有“AI 腔”的排比、升华、设问和空词。
- [ ] 限制和失败情况写在了显眼位置。
- [ ] 链接可点，备案号正确。
