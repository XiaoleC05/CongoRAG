# 文档处理管线

文档从上传到能被检索到，要经过一条固定的链路：上传、落盘、入库、解析、切分、向量化、写回索引。每一步的产物都能被单独观察，出了问题也能定位到具体是哪一步失败。

上传阶段只做两件事：把字节写进磁盘，写一行文档记录。这时文档还没有任何分块，检索不到它。请求返回的是被接受的语义——文件收到了，处理是异步的，不是已经处理完了。

解析和切分属于同一层。解析把原始文件读成纯文本，切分把纯文本切成若干个分块。当前的切分策略是按空行分段，再把段落贪心地装进不超过 1200 个字符的块里；只有当某个段落本身就超过这个上限时，才会退化成按字符数硬切。这个策略的优点是行为可预测、切出来的边界和作者写的段落边界一致，缺点是它完全不理解 Markdown 的标题层级和列表结构。由此可以推出一个实用的结论：一个不超过 1200 字的段落，必定完整地落在某一个分块里，不会被切开。

切分粒度直接决定检索的效果。块切得太细，一段完整的论述被打散，检索命中的是半句话，模型拿到的是不完整的证据；块切得太粗，一个块里混着好几个主题，向量被平均成一个谁都不像的方向，检索反而更不容易命中。段落边界之所以是个不错的默认值，是因为作者本来就用空行分隔了语义单元。

向量化是整条链路上唯一需要外部服务的一步。每个分块被送进嵌入模型，换回一个固定维度的向量，连同分块正文一起写进数据库。向量化失败通常意味着上游模型服务不可用或者配置不对，这一步的失败是可以重试的。

入库是最后一步，也是唯一会改变检索结果的写操作。它先删掉这份文档已有的全部分块，再插入新的分块。删除加插入是一个整体，中途失败不会留下半份旧分块。重新处理一份文档（换嵌入模型、修好一次失败、调整切分策略）走的就是这条路。

这条链路上有一个容易被忽视的事实：分块的主键是随机生成的，每次重新处理都会换一批新的主键，插入时的顺序也不代表任何稳定的顺序。任何依赖记住某个分块标识的做法，都会在下一次重新处理之后失效。跨运行稳定的只有分块的内容本身，所以任何需要跨运行比较的判据都应该建立在内容上，而不是标识上。
