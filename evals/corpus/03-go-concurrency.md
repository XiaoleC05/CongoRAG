# Go 的并发模型

goroutine 是 Go 运行时调度的轻量级执行单元。它的初始栈很小，按需增长，创建和销毁的开销远低于操作系统线程，因此在一个进程里同时跑几千个 goroutine 是常规做法，不需要线程池那一层额外的抽象。

channel 是 goroutine 之间传递数据的通道。Go 的并发箴言是不要通过共享内存来通信，而要通过通信来共享内存——把数据放进 channel，所有权就跟着一起转移了，接收方拿到的是独占的副本，不需要再加锁。有缓冲的 channel 允许发送方在缓冲没满时不被阻塞，它更像一个队列；无缓冲的 channel 则要求收发双方在同一个时刻会合，天然起到同步点的作用。

context 用来在调用链上传递取消信号、超时和请求范围的值。它的约定是：谁创建谁负责取消，取消函数必须被调用，否则会泄漏计时器；context 应该作为函数的第一个参数显式传递，不要塞进结构体里存起来；业务数据也不该放进去，它不是可选参数的替代品。

当多个 goroutine 需要访问同一份数据时，标准做法是用 sync.Mutex 保护临界区，或者干脆让它们各自持有自己的副本、最后再合并。选哪一种取决于数据有多大、访问有多频繁：小结构体加锁更简单，大结构体或写多读少的场景倾向分片或者用消息传递把写操作串行化。

并发不是越多越好。同时跑的任务数超过机器能真正并行处理的数量之后，多出来的部分只是在抢占和排队，吞吐不再上升，延迟反而变差。给并发设一个上限，让超出的请求排队等待，比无限放开更能保证尾延迟。

还有一个容易被忽略的点：goroutine 泄漏。一个 goroutine 如果永远阻塞在一个没有人会再发送的 channel 上，它就永远不会退出，它引用的内存也永远不释放。给每个可能长期阻塞的操作配一个 context 超时，或者提供一个明确的关闭信号，是避免这类问题的常规手段。
