# 向量检索与 pgvector

pgvector 是 PostgreSQL 的向量扩展。它给数据库加了向量类型、向量距离运算符和向量索引。ConGoRAG 用它来存文档分块的嵌入向量，并且直接在 SQL 里做最近邻查询，不需要再引入一个专门的向量数据库——检索和业务数据在同一个事务、同一个备份里，少了一套需要单独运维的组件。

向量列的类型是 halfvec，也就是半精度浮点向量。相比完整的 float4 向量，半精度把每个维度的存储从四字节压到两字节，索引体积和内存占用都明显下降，而召回质量在绝大多数语料上几乎看不出差别。代价是数值精度更低，对极小的取值不敏感，但这不影响谁离查询更近这个排序结论。

HNSW 是 pgvector 提供的近似最近邻索引。它把向量组织成多层图，查询时从稀疏的上层快速跳到目标区域附近，再在稠密的下层做局部搜索。因为只访问了图里的一小部分节点，它比逐行计算的精确扫描快得多，代价是可能漏掉真正最近的那几条——这就是近似两个字的来源。

ef_search 是 HNSW 的查询期参数，控制搜索时维护的候选集合大小。把它调大，搜索会访问更多节点，召回率上升、耗时增加；调小则相反。这个参数可以在会话级别临时设置，不必重建索引，所以它很适合用来做召回率换延迟的现场实验。

索引的构建和维护也有取舍。HNSW 建索引比顺序扫描慢，写入时还要额外维护图结构，所以索引不是免费的。语料很小的时候，精确扫描本来就只要几毫秒，索引带来的复杂度换不回可感知的收益；只有当分块数量涨到几万、几十万，顺序比较全表开始变慢，索引的价值才显现出来。判断要不要索引，看的是分块的绝对数量，不是文档的份数。

精确扫描和近似扫描的差异可以用一个简单的办法量出来：把同一批查询分别走这两条路径，比较各自返回的 top-K 有多少重合。这个重合比例就是常说的 recall@K。它衡量的是索引相对全量计算漏掉了多少，不是回答对不对；分母是精确扫描的结果，不是人工写的标准答案。这一点容易混淆，量出来的数字再好看也不能直接当成问答质量。
