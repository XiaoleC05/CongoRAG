# ADR-008：幂等重放的响应快照与保留窗口

- 状态：已采纳
- 日期：2026-09-22
- 相关：`internal/conversation/usecase.go`、`internal/agent/usecase.go`、
  `contracts/openapi.yaml`、`docs/sse-protocol.md`、`docs/adr/007-recovery-semantics.md`

## 背景

项目文档 §8.3 把两件事留成待定项：

> 要定：**响应快照**（重放时返回什么）和**保留窗口**（多久后同一个 key 可再执行）。

v3.0 实现幂等重放时**只定了会话消息那一侧的行为**（把那一轮已记录的事件按
原 `event_id` 补发一遍，键保留 24 小时，见 CHANGELOG v3.0）。Agent run 这一侧
（`POST /api/v1/agents/{id}/runs`）也要带幂等键（§8.3 原话是
「`POST messages` **和** `POST runs` 都带」），但不定的代价是行为随实现漂移：
同一个键在两个端点表现不一致，而两端都叫「幂等」。

## 决策一：run 端点重放时返回什么

**最小快照 = `run_id`，由流的首帧承载；其余内容走事件补发。**

具体形状：

1. `POST /api/v1/agents/{id}/runs` 的响应流**首帧**是 `run_started`，
   `data: {"runId": "<uuid>"}`。这一帧在**新建**和**命中重放**两种情况下都发，
   形状完全相同——客户端不需要为「重发」写第二套解析逻辑。
2. 命中已有键时，服务端**不重新执行**，接着把该 run **已记录的事件**
   （`run_events`，按 `event_id` 升序）补发一遍，帧类型与真实 `event_id`
   和原请求一致，补完即结束响应。
3. 客户端凭首帧里的 `run_id` 可以在任何时候调
   `GET /api/v1/runs/{runId}/events?after_event_id=N` 重新订阅。

**为什么不是「只有 run_id」**：POST 的响应体是一条 SSE 流，只给一个 id 就无
内容可发；而且会话那一侧已经确立了「命中即补发同一轮事件」的语义，两端不一致
会让「幂等」这个词在两个端点意味着两件事。

**为什么不是「完整 run 快照」**：`agent_runs` 里有两列不该出现在 API 资源里——
`state_snapshot`（业务 checkpoint，格式由我们自己演进，见
[ADR-006](006-checkpoint-layering.md)）与 `state_schema_version`（内部版本号）。
把它们塞进响应，等于把一个内部结构变成对外承诺。

### 顺带解决的一个真实缺口

在这条决策之前，`POST runs` 的流里**没有任何地方带 run id**——
`token` / `tool_call` / `tool_result` / `error` / `done` 五种事件都不含它。
也就是说客户端发起一次运行之后根本不知道自己这次运行叫什么，
而「取消」（`POST .../runs/{runId}/cancel`）恰恰需要这个 id。
`run_started` 把这条补上，这是它会出现在**新建**路径上的理由，
不只是为了重放。

## 决策二：保留窗口

**与消息路径共用同一个值：24 小时。** 也就是同一份常量，不是两个各写一遍
的 `24 * time.Hour`。

理由有两条：

- **语义上它们是同一件事**（「一个幂等键在多长时间内有效」）。两个值意味着
  将来改一个忘一个，而两边都叫幂等，漂移不会被任何测试或编译错误发现。
- **24 小时这个数字对 run 同样成立**，而且理由更强：消息路径之所以不需要更
  长的窗口，是因为键的用途是**覆盖一次客户端重试**（秒到分钟级）。
  run 比消息更贵，但「贵的操作更需要自动去重」不等于「窗口要更长」——
  隔了一天之后用户再点一次「运行」，本来就应该真的跑一次。

实现落点：`internal/platform` 暴露一个共用常量，两处引用它。

## 决策三：过期之后同一个键再来会怎样

**重新执行**，不是报错。

判据是「服务端还剩什么可依据的」：键过期后行已经被清掉（
`ReserveIdempotencyKey` 顺手删过期行），服务端**没有任何记录**能证明这个键
出现过。这时唯一自洽的行为是把它当成一次全新的请求。报错的话，
「昨天点过、今天再点」会变成一个用户无法理解的失败，而且他没有任何办法
绕过它——这是本项目最忌讳的那类故障。

这条有测试钉住（过期行被清掉之后，同一个键第二次调用会真的执行第二次），
不是只写在文档里。

## 后果

- `docs/sse-protocol.md` 的事件类型表新增 `run_started`，并说明它在新建与
  重放两条路径上都会出现、且必须是首帧。
- 契约里 `POST /api/v1/agents/{id}/runs` 加上 `Idempotency-Key` 请求头参数，
  描述里写明「命中即补发 + 首帧给 runId」，以及 24 小时的窗口。
- 前端（停止按钮、run 详情跳转）从此有一个稳定的 run id 来源，
  不需要再靠列表接口反查。
- **两条路径的事件补发都不跨进程持锁**：补发只读已落库的事件，发完即结束，
  与会话维度那条 `GET /events` 保持同一条语义。
