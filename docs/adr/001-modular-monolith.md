# ADR-001：模块化单体 + 单 Worker，不做微服务

- 状态：已采纳
- 日期：2026-09-20
- 相关：技术方案 §一「架构选型决策（ADR-001）」、代码架构设计 §2 的包划分

## 背景

ConGoRAG 是一个本地单机部署的知识库 + RAG + Agent 平台（技术方案 §一：
「本地运行……本机 Docker 一键部署」）。系统要做的事——知识库管理、文档处理、
向量检索、会话、Context 管理、Agent 执行——天然分成好几块职责，需要决定
这些职责之间是进程边界还是包边界。

## 决策

**一个 API 进程 + 一个 Worker 进程，模块边界用 Go 的包表达，不拆微服务。**

- `apps/api`：Gin + 生成的 REST 接口层，内嵌前端静态产物，处理所有同步请求
  和 SSE 流式响应（Agent 实时执行、LLM streaming 全部在这个进程内完成）
- `apps/worker`：River 消费端，只做异步批任务——文档解析/切分/向量化、
  全量重嵌入、孤儿文件对账
- 两个进程共享 `internal/` 下的 8 个业务包（`domain`/`platform`/`llm`/
  `knowledge`/`retrieval`/`ctxmgr`/`conversation`/`agent`），包之间的依赖
  方向由代码架构设计 §2.1 的表固定，用 `internal/arch_test.go` 之类的
  编译期/测试期断言强制

没有 API Gateway、没有服务发现、没有独立部署的"用户服务""知识库服务"。

## 理由

1. **部署边界是本地单机应用**（技术方案 §一）。微服务解决的是"多团队独立
   发布""按负载独立扩容"这两类问题，两者在这里都不存在——只有一个开发者，
   运行环境是用户自己的电脑，负载来自这一台机器上的这一个用户。为不存在的
   问题预先付分布式系统的成本（网络分区、服务发现、跨服务事务、分布式追踪）
   是不必要的复杂度。

2. **PostgreSQL 单库承载一切**（技术方案 §二的核心原则：「PostgreSQL =
   Source of Truth」）。业务数据、向量（pgvector）、异步队列（River 用
   PG 做队列）全在一个数据库里，事务性入队（`riverClient.InsertTx`，
   技术方案 §四的模式表）因此能用一个数据库事务同时保证"业务记录写入"和
   "任务入队"的原子性——这在任务队列是独立系统（如 Redis/RabbitMQ）时
   做不到，微服务架构下更是要额外引入 Saga 或两阶段提交之类的补偿机制。

3. **模块边界保留拆分接缝，不是永久焊死**。8 个包之间用 port（接口）
   通信，不直接访问对方的内部实现（代码架构设计 §1.2 规则 A）；跨包传递
   的数据用 `domain` 的中性类型，不是各包私有的结构体。这意味着如果将来
   真的需要拆出一个包成独立服务，边界已经在——用 gRPC/HTTP 替换掉 Go 的
   函数调用，不需要先重新设计模块职责。

4. **零分布式成本换清晰的职责划分**。用 Go 的包（不是微服务）分职责，
   拿到了"关注点分离"的好处（`agent` 不认识 SQL，`knowledge` 不认识
   Eino），却不用付分布式系统的代价（网络超时处理、幂等重试跨服务传递、
   分布式追踪、多个部署单元的版本兼容）。技术方案自己的结论是「简单是
   设计纪律」——这条决策是这句话在架构层面的落地。

## 后果

- **好处**：本地部署只需要 `docker compose up -d`（`postgres`/`api`/
  `worker` 三个容器），没有服务网格、没有独立的配置中心；调试时能在一个
  进程里单步跟完一次请求的大部分路径（除了真正跨进程的 River 任务）；
  测试不需要模拟网络分区。

- **代价**：`api` 和 `worker` 各自的装配根（`apps/api/internal/app/`、
  `apps/worker/internal/app/`）之间有十几行重复代码——两边都要接
  `pgxpool` + `platform` + `llm.Registry` 等基础设施。代码架构设计 §6
  明确记录了这一点并给出理由：为了消掉这点重复去造一个共享装配包，会
  把 8 个包变成 9 个，并让两个进程互相绑死，代价比留着重复更大。

- **如果将来要重新考虑**：负载来源从"单机单用户"变成"多用户共享部署"，
  或者某个模块（比如向量检索）需要独立于其它模块弹性扩容时，需要重新
  评估这条决策——那时候 `retrieval` 包已经是一个通过 port 通信的独立
  单元，拆分成本比一开始就是分布式架构、但从没受益于这个决策的项目更低。
